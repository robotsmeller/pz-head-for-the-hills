# Head for the Hills! - Project Rules

## What this is

A Project Zomboid Build 42 start-scenario mod. The player wakes up at a hand-picked remote cabin, stocked with basic supplies and a vehicle, with a zombie-free buffer immediately around the cabin and a real drivable stretch to the nearest town for anyone who wants to push their luck.

## Hard-won B42 facts (verified empirically by sibling projects, not guessed)

- **B42 silently rejects a mod missing `42/mod.info`.** Root `mod.info` alone is not enough - the mod won't appear in the in-game mods list and nothing gets logged to `console.txt`. Keep root and `42/mod.info` in sync on every change. Verified against a live 180-mod install by `pz-mod-checker` (session 9) and applied to `unbreaker`'s own shipped structure.
- Vanilla `spawnpoints.lua` keys point lists **by profession** (`chef`, `unemployed`, `farmer`, etc.), not as one flat randomized list per region. Getting 2-3 cabins to randomize regardless of chosen occupation means either mapping every profession key to the same point list, or defining one dedicated occupation for this scenario.
- Real vanilla reference lives on disk, not just in blog posts: `C:\Program Files (x86)\Steam\steamapps\common\ProjectZomboid\media\lua\shared\SpawnRegions.lua` and per-town `spawnpoints.lua` under `media\maps\<Town>\`. Read the real files before guessing at API shape or field names.
- `SpawnRegionMgr.getSpawnRegionsAux()` looks for `media/maps/<mapname>/spawnregions.lua` first, falling back to an auto-generated region per loaded map. A custom "Remote Cabin" region needs to hook in via the mod's own Lua rather than editing vanilla files directly.
- **B42.20 restricts `getFileWriter` to a whitelist of file extensions.** Measured on 42.20.0 (session 2): `.txt`, `.ini`, `.cfg` open fine; `.json`, `.dat`, `.tmp` return **nil**. The append flag and root-vs-subdirectory make no difference, only the extension does. `getFileReader` is unaffected, so `.json` stays readable and a mod that only reads config never notices. Because the failure is a nil return rather than a throw, it surfaces later and elsewhere as `attempted index: close of non-table: null`. Double extensions are judged on the last one, so `foo.json.ready` is rejected for `.ready`. This broke `pz-test-pilot` completely; rule `b42-20-getfilewriter-extension-whitelist` in `pz-mod-checker` now catches it. Caveat: only those six extensions were tested, so treat `.txt`/`.ini`/`.cfg` as known-good rather than as the complete whitelist.
- Native Sandbox Vars **enum** dropdowns are parsed from a static `sandbox-options.txt` before any mod Lua runs, so their choices cannot be generated at runtime. To offer a list built from what is actually installed, declare the option as `type = string` and replace its control by wrapping `SandboxOptionsScreen:createControlForSetting`. The screen persists whatever sits in `self.controls[name]` via `control:getText()`/`setText()`, so a custom widget that implements those two methods rides the normal per-save sandbox system with no extra persistence layer and no second settings screen. This is how the live vehicle and equipment pickers work (`mod/42/media/lua/client/HeadForTheHills/SandboxPickers.lua`).
- `getScriptManager():getAllVehicleScripts()` and `:getAllItems()` enumerate everything currently loaded, vanilla plus enabled mods (measured: 506 vehicles, 7839 items on a modded install). `Item:getDisplayName()` is safe across all of them (0 failures in 7839), but `VehicleScript:getDisplayName()` **throws** - it does not exist on that class in B42, so use `getName()`/`getFullName()`.
- **A B42 well is an entity, not a prop.** `Base.Well` is declared in `media/scripts/generated/entities/appliances/workstations/entity_well.txt` on sprite `camping_01_16`, with a `FluidContainer` component (capacity 10000, fills with clean water, 20-100% initial). To place a working one from Lua, follow `server/Map/MapObjects/MORainCollectorBarrel.lua`: build an `IsoThumpable`, get the script via `SpriteConfigManager.getObjectInfoFromSprite(sprite)` then `:getScript():getParent()`, hand both to `GameEntityFactory.CreateIsoObjectEntity(obj, script, true)`, then `square:AddSpecialObject(obj)`. Verified live (session 3): the placed well came back with a real filled `FluidContainer`. An `IsoObject.new` with the right sprite would be decorative only. Going through the script also means an override like the `MyOwnWell` workshop mod is picked up automatically rather than fought.
- **`SandboxVars.StartMonth` is consumed at world creation, so writing it during `OnNewGame` does nothing.** Measured (session 3): the var read back as January while the clock sat in July. `getGameTime():setMonth()` does move it. Watch the indexing - `StartMonth` is **one-based** (7 = July) and `getGameTime():getMonth()` is **zero-based** (6 = July). There is no `getGameTime():getSeason()`; season lives on `getClimateManager():getSeason()` as an `ErosionSeason`.
- **`IsoGenerator` fuel is capped at `getMaxFuel()`, which is 10, and the UI shows that cap as 100%.** So `setFuel(100)` clamps *down*. Use `setFuel(generator:getMaxFuel())`. `setActivated` is gated on having fuel, so fuel must go in before `setConnected`/`setActivated`. The item's `getModData().fuel` **does** carry across the `IsoGenerator.new` constructor, but is not clamped. Vanilla map generators are created at condition 100 with **zero** fuel (`MOGenerator.lua`), so a generator found on the map is dead until something starts it.
- **Starting a generator from inside `OnNewGame` does not stick.** Measured live (session 4): a generator created and started there read back `fuel 0`, `isConnected() false`, `isActivated() false`, with **no error raised** - and at condition 100 on sprite `appliances_misc_01_0`, which is exactly what `MOGenerator.lua`'s `ReplaceExistingObject` builds. That file registers `MapObjects.OnNewWithSprite` handlers on those very sprites, so a map-object pass over the chunk after our write is the likely culprit. Ruled out first, by measurement rather than reasoning: the option was a real `true` in both `SandboxVars` and `getSandboxOptions()`; `StartMonth=4` proved `applySeason` read `Season` correctly in that same event; the identical `instanceItem` -> `IsoGenerator.new` -> `setFuel`/`setConnected`/`setActivated` sequence works when run a moment later (`0/10` -> `10/10 conn=true act=true`); and re-firing `triggerEvent("OnNewGame", ...)` in a loaded world passes. Fix: re-apply the running state on a later `OnTick`, once the world is up. Same family as the ghost vehicle below - do not mutate a chunk that has not settled.
- **`triggerEvent("OnNewGame", player, square)` works from Lua** and is the only practical way to exercise spawn logic without rolling a world per branch. Vanilla uses the bare global in `shared/Foraging/forageSystem.lua`.
- **Vanilla classifies ground by floor-sprite name, not by a flag.** `server/BuildingObjects/ISShovelGroundCursor.lua`'s `GetDirtGravelSand()` returns `"dirt"`/`"gravel"`/`"sand"`/`"clay"`: anything under `blends_natural_01_` or `floors_exterior_natural` is dirt or grass, minus an explicit exclusion list for the other three. Grass needs no separate test - PZ draws it as the natural blend itself, not as an overlay. Water is the floor sprite's own flag, `getFloor():getSprite():getProperties():has(IsoFlagType.water)` (`ISWoodenStairs.lua`, `buildRecipeCode.lua`), plus `IsoFlagType.taintedWater` on the *square* properties for river and pond tiles.
- **Most `IsoObject`s have no `isDoor` method, and calling it anyway costs a full Java stack dump.** `pcall` catches the throw, but PZ still writes the whole trace to `console.txt` - measured at **234 dumps in a single world start** from one placement search. `type(object.isDoor)` returns `nil` on a plain `IsoObject`, so field-test before calling (`object.isDoor and object:isDoor()`) instead of guarding with `pcall`. Same shape as `gen.isConnected and gen:isConnected()` in the GeneratorNetwork mod.
- **`square:getBuilding() == nil` does not mean "clear of the building".** It only answers "is this square inside the footprint", so a ring search from the player finds the square hard against the outside wall and puts the well there. Distance from a building needs its own neighbour scan.
- **Spawning a vehicle into building geometry produces chunk-orphaned ghosts.** Measured (session 3): `addVehicle` on a square two tiles from a player standing inside a house gave a car that rendered as a floating shadow, logged `IsoChunk.removeFromWorld: vehicle wasn't removed from world`, and did not survive a reload while its key stayed in the player's inventory. Vanilla does the same call in `OnNewGame` (`shared/Items/SpawnItems.lua`) but only at hand-picked open coordinates. Require real clearance, not one free tile.
- Vehicle-part mods can attach parts **after** `addVehicle` returns. A condition pass run during `OnNewGame` therefore misses them - measured with `DAMNBumperFront`, `DAMNBumperRear` and `DAMNSpareTire` keeping their own condition while all 42 other parts took ours.
- **Vanilla hands every new character an ID card.** `shared/Items/SpawnItems.lua` (~line 176) does `AddItem("Base.IDcard")` unconditionally, swapping to `Base.Passport` only on a `SpecialKeyRingChance` roll. Any mod that also grants one produces two, which is #9. Compounding it, four vanilla items share the display name **"ID Card"** exactly (`IDcard`, `IDcard_Female`, `IDcard_Male`, `IDcard_Stolen`), so a picker listing display names looks like it has duplicate rows when it does not. Vanilla's handler is registered first because vanilla Lua loads before mod Lua, so a mod's `OnNewGame` runs second and can see what vanilla already granted.
- **`ItemContainer:haveThisKeyId(id)` returns the Key item or nil, not a boolean.** Measured live: `Base.CarKey:zombie.inventory.types.Key@c6d57c7` for a match, `nil` otherwise. Comparing it to `true` is therefore always false and silently disables whatever it guards. Every vanilla call site truthy-tests it (`ISStartVehicleEngine.lua`, `ISOpenVehicleDoor.lua`). Matching `vehicle:getKeyId()` against the player's keys is the only exact way to tell the mod's vehicle from a map one; proximity picks whatever is parked nearest.
- **`IsoPlayer:setX/setY` does not teleport, and it fails in the most misleading way available.** Measured live (session 6): the call takes and `getX()` reads back the new coordinates immediately, then about a second later the character is back where they started. The *square* never changes at all, because nothing about setting a coordinate asks for the destination chunk to load (`getSquare()` there returns nil throughout). `setLx`/`setLy` do not exist on B42's player - `type()` reads nil, so calling them throws. **`getPlayer():teleportTo(x, y, z)` is the one that works**: measured over 12 hops it landed the player exactly on target every time and streamed the destination chunk in, with `getCurrentSquare()` catching up inside a second. Related: pz-test-pilot's own `teleport` command never moves the player at all on B42.20, throwing `Object tried to call nil in teleport java.lang.RuntimeException` on all 12 hops. That corrects the earlier reading in this file, which had it moving the player first and throwing afterwards; the session-6 run disproved that.
- **`getCell():getVehicles()` does not exist in B42, and it throws straight past `pcall`** as `Object tried to call nil`, same as `VehicleScript:getDisplayName()`. Field-test with `type()` or `obj.method and obj:method()`, or scan squares with `getVehicleContainer()` and dedupe on each vehicle's anchor square. Same lesson as `isDoor`: field-test, never `pcall`.

## Related tooling (same author, `c:\xampp\htdocs`)

| Project | Use it for |

| `pz-test-pilot` | **Its `run_lua` result is at `response["data"]["result"]`, not `response["result"]`** - `CommandRouter.dispatch` answers `{id, command, status, data, tick}` and `Core.writeResult` writes that verbatim. Reading `result["result"]` with a `.get(k, result)` fallback silently returns the whole envelope, whose repr still contains `=` and `|`, so a parser downstream yields plausible nonsense instead of failing. `tests/_pilot.py` has the one correct accessor; go through it. Driving a running PZ instance to verify spawn location, starting kit, and zombie density without manual in-game testing. Already deployed as a symlink at `Zomboid/mods/PZTestPilot` - no sync step, and there is no `launch.py`. Send commands with `python scripts/cmd.py <action>`; `run_lua` executes arbitrary Lua in the running game. The harness only registers on `OnGameStart`, so it can verify anything in a loaded save but cannot drive main-menu screens. Its IPC files are `.txt` (not `.json`) because of the B42.20 restriction above - do not "fix" them back. This project's own checks live in `tests/api_checks.py`. **`harness_dead` is often a false positive:** the liveness check measures in-game ticks, which stop when PZ loses focus, so a command sent while the user is tabbed away reports a dead harness after having dispatched and completed normally. Read `Zomboid/Lua/TestPilot/result.txt` before believing it, and check `log.txt` for the `Dispatch:` line. Worth fixing in that repo. **Its `teleport` command is broken on B42.20:** it logs `Command teleport failed: Object tried to call nil in teleport`, but it moves the player *first* and throws on a follow-up call, so a failed status does not mean the player stayed put. Never send it and ignore the reply - every scan here is centred on the player, so silently landing elsewhere makes a test measure the wrong square and report a healthy object as missing. `verify_generator.py`'s `teleport()` warns and then confirms the landing position. |
